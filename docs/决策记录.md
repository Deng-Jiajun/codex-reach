# Codex Reach 决策记录

整理日期为 2026-11-11。需求以 [产品规格](产品规格.md) 的当前内容为准，本文保留影响后续工作的选择依据、已替代方案和待确认事项。

原始讨论来自 [评估安卓端访问 Codex 方案](thread://01a1a585-932b-7731-ac8f-a0bbfacb741a?hostId=local)。2026-11-11 的最新交互要求与文档整理要求来自 [修复 codex-reach 对话列表与属性](thread://01a1cb24-8fe0-7632-9686-05f9ea933932?hostId=local)。

## 接入现有 Codex App

**已确认方向**。主要场景是在外通过手机管理电脑上已有的 Codex 对话，继续使用桌面的项目、聊天标识、执行环境和置顶结果。

原 Qoder 转发存在用户反馈的连接不稳定和额外中转问题。官方安卓入口在用户当前体验中加载慢、依赖代理，最终转向自建 Tailscale 手机入口。

当前适配组合使用 App Tools 处理项目、对话组织及部分发送操作，桌面 IPC 处理实时状态与执行交互，App Server 读取历史及目录数据。独立执行实例与会话转换曾被讨论，当前采用桌面继续执行的方案。

## 从 Farfield 转向自建

**已确认选择**。Farfield 本机适配曾跑通核心收发流程。后续用户反馈字体和操作体验不足，协议适配多次修复，维护投入超出预期，明确倾向自建 Rust 服务与 H5。

源码分析还发现全量会话状态重复传输与重复获取路径，形成历史分页、有限范围更新和减少重复请求的性能方向。用户要求对流量问题做源码静态分析，并明确结束网络详情追问。观察到的上传流量未完成量化归因。

Rust 是已选技术栈。此前语言性能讨论没有形成 Rust 相对 TypeScript 在本项目中的实测优势结论。已有接入经验和验证样例继续作为适配依据。

## APK、SQLite 与构建环境

**已确认选择**。采用 Rust 本地服务、H5、Capacitor Android APK 和手机原生 SQLite，GitHub Actions 承担 Android 编译、签名、打包与自动检查。

用户希望尽量减少本机环境依赖，并倾向 APK 的使用体验。Android Studio 按具体原生问题需要使用，本机日常开发使用 Rust、Node.js 和浏览器。

用户对大量本地存储的需求较弱，核心要求是已看过的内容和草稿能够快速恢复。SQLite 已通过模拟器与 REDMI K80 Pro、Android 16 的合成数据检查；选型依据包括分页、事务和可控存储，SQLite 与 IndexedDB 的本项目性能对比没有实测记录。

早期 PWA、IndexedDB 和浏览器持久化授权讨论属于选型过程。当前手机主交付为 Capacitor APK 与原生 SQLite。

首个验证包的临时签名仅属于历史构建做法。后续版本沿用固定签名升级流程。

## Windows 登录启动

2026-11-12 用户在重启电脑后提出开机启动项需求。服务使用当前用户的 Codex 桌面管道，采用当前用户登录 Windows 后隐藏启动；Codex 已有登录启动项，Tailscale 系统服务为自动启动。

程序与网页放到固定运行目录，沿用原配置和发送记录。启动器等待配置中的监听地址可用后启动服务，避免 Tailscale 地址尚未出现时绑定失败；服务独立运行，启动器随后退出。已通过同一入口的手动启动和重复启动检查，重新启动电脑后的登录触发仍待复测。

## 界面风格与状态表达

**已确认方向**。Qoder 移动端的简洁风格作为主要参考。原方案同时参考 Happy 的参数选择、HAPI 的任务设置、RikkaHub 的消息阅读与操作，这些属于设计参考。

用户已提出并在原对话推进过以下要求。

- 标题与会话信息集中到同一顶部栏
- 设置用齿轮图标，刷新用图标与旋转状态
- 左上角返回与 Android 返回键行为一致
- 设置页返回保留原对话、滚动位置和草稿
- 首次读取、历史分页和最新消息同步给出明确反馈
- 单个对话读取失败单独报错，连接状态按实际连接情况显示

**已确认隐藏 `notLoaded`**。用户曾问「这有啥用？是看不了历史对话还是什么？」。原对话随后确认该字段表示执行实例的加载状态，历史可读性另由查询结果判断，并在 `0.5.0-preview` 隐藏显示。本次用户再次指出该背景，重新显示「未加载」的改动已撤回。

## 最近轮次允许编辑

**已确认需求**。用户明确说明误触发送后的编辑是正常使用行为，最近一轮即使已经完成也可能变化。缓存与同步需要更新被替换的用户消息及后续回复。

早期“历史全部不可变”和只靠会话时间判断具体变化的简化前提已修正。后续核实桌面实时流已有 `baseRevision/revision`，可以校验增量连续性，重连可获取新快照。逐条消息的持久编辑版本号仍缺少已确认接口依据。

## 侧聊、引用与分支

**后续明确决定优先**。

## 过程折叠与 Add to chat

2026-11-12 用户要求合并工具记录与思考摘要，并参照 Codex App 折叠中间过程、保留最终输出。采用每轮连续过程分组，按已有消息阶段识别中间进度；不折叠待回答问题和附件，缺少阶段的旧回答继续显示。

用户明确选择「按 Add to chat 改为选段并附上意见」。界面改名「添加到对话」，保留选段、意见和来源位置，显示为可修改的草稿卡片；普通输入草稿独立保留，发送时组装为桌面可识别的选段上下文。未选中文字时先选择片段，取消“未选择就摘录整条消息”的原行为。

用户在 `0.5.1-preview` 验收后进一步明确：连续工具记录、连续思考摘要应分别合并折叠；选择回答正文后直接显示悬浮面板。保留外层「执行过程」，内部按连续类型分组；「添加到对话」改为选区附近的悬浮入口，移除消息末尾按钮，继续复用选段与意见卡片。`Ask in side chat` 沿用此前跳过的决定。

## 置顶与参数入口

**本次已确认的交互要求**。置顶属于对话基本属性，图钉放在对话标题前，列表和聊天页都能直接设置或取消置顶，原「对话操作」入口中的置顶操作迁出。

用户同时要求改善模型、思考深度、新建对话和属性查询的等待。已有属性应复用，重复请求与正文读取的耦合需要检查。缓存时长、后台刷新方式等尚属实现取舍。

当前下一轮参数的生效规则见产品规格。改变为立即写入桌面会话默认参数的行为尚未讨论确认。

## 验收结论的适用范围

原对话采用分批实现、开发侧自行核验、用户最终手机验收的方式。`0.5.0-preview` 的测试通过记录覆盖当时已执行的自动检查和部分真实桌面操作，手机交互、系统文件选择器、Tailscale 使用体验和真实长对话性能仍属于最终验收内容。

本次截图已经提供新的缺陷依据。当前状态应记为「已交付预览版本，继续处理真机反馈」，后续修复分别记录实现、测试和交付结果。

## 本轮基本属性读取调整

已核实桌面读取当前模型时优先采用 `latestCollaborationMode.settings.model`，再取 `latestModel`，思考深度取 `latestReasoningEffort`。Reach 采用同一读取规则，已有实时参数的面板直接展示；缺失时通过原接口读取，选择下一轮参数可独立进行。模型目录按连接保存并合并并发请求。

置顶状态优先取列表已有属性，新建对话使用已知的初始未置顶状态；恢复的对话尚未取得置顶属性时单独读取。操作后同步列表与聊天图钉，并处理较旧列表响应覆盖新结果的问题。

## 2026-11-12 撤回五分钟目录缓存有效期

用户指出关注的是单次查询为何缓慢，以及基本属性变化如何及时同步。五分钟有效期由开发时自行选择，缺少测量依据，已移除。可选模型目录改为打开选择器时重新查询，保留并发请求合并与已加载选项的先行展示。

本机计时已将旧置顶查询的主要等待定位到桌面 `list_threads(recent)`，约 2.6 秒。模型目录预热后的读取与当前会话参数读取为毫秒量级，手机所见额外等待尚缺端到端计时。

当前会话状态和参数走 IPC 事件及版本同步。置顶的外部变更仍依赖刷新列表，完整实时置顶同步尚未实现。后续若接入置顶事件，需验证它与桌面侧栏的实际数据来源一致。

本轮已通过浏览器检查，空闲标签隐藏，执行状态仍显示；每次打开参数面板重新读取模型目录，刷新保留当前选择，实时参数变化直接更新已打开面板。相关 Rust 测试、前端构建和同步测试通过，Android 真机验收待执行。
