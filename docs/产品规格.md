# Codex Reach 产品规格

更新日期为 2026-11-12。本文记录当前有效需求与验收要求。方案依据及修订过程见 [决策记录](决策记录.md)，安装与使用见 [README](../README.md)。

## 当前范围

手机通过 Tailscale 连接电脑上的 Reach 服务，查看和操作现有 Codex App 的同一批项目与对话，任务继续由电脑执行。主要使用设备为 REDMI K80 Pro、Android 16。

当前方案为 Rust 本地服务、H5 界面、Capacitor Android APK 和原生 SQLite。项目名为 Codex Reach，仓库名为 `codex-reach`，使用公开 GitHub 仓库。访问凭据、签名私钥、真实聊天数据和本机运行配置保存在仓库外。

本轮交付版本为 `0.5.2-preview`，Android `versionCode` 为 9，签名与 `0.5.1-preview` 一致。连续同类记录合并与选区悬浮入口已通过本地检查和 Android 16 模拟器原生长按、点击验证。[本版 CI](https://github.com/Deng-Jiajun/codex-reach/actions/runs/43142142397)

## 功能与行为

| 功能 | 当前有效要求 |
| --- | --- |
| 服务启动 | 当前用户登录 Windows 后隐藏启动，等待配置的监听地址可用；启动器退出后服务继续运行，Codex 与 Tailscale 保持运行 |
| 连接 | 明确显示连接状态，断线自动重试，并提供立即重连入口 |
| 项目与对话列表 | 按项目筛选，分页读取，搜索已加载标题，显示正确的更新时间 |
| 新建对话 | 选择项目或独立目录、模型和思考深度，提交首条消息时创建 |
| 置顶 | 与桌面侧栏同步，列表优先展示置顶对话；聊天标题和列表标题前提供图钉，直接设置或取消置顶 |
| 消息 | 发送、执行中追加；中间进度、公开思考摘要和工具记录合并折叠，最终回答保持展开；保留输入草稿 |
| 模型与思考深度 | 作为基本参数提供直接入口，深度选项随模型变化；明确展示当前会话参数与下一轮选择的适用范围 |
| Skill | 查询当前项目可用 Skill，选择用于下一次发送，成功投递后清除本次选择 |
| 停止 | 针对当前正在执行的轮次发起停止；轮次变化后重新读取状态 |
| 编辑 | 编辑最近一条原生用户消息，重新执行并同步被替换的回复，保留原有附件与普通输入草稿 |
| 审批与问答 | 手机处理命令、文件、权限审批、普通问题及可完整展示的标准 MCP 表单 |
| 添加到对话 | 选择回答片段并附上意见，以卡片保存原文、意见和来源位置；与当前输入草稿一同发送 |
| 附件 | 浏览电脑文件与目录，上传手机文件，发送附件，显示路径并预览支持的图片 |

「创建完整历史分支」按本次明确要求移除。`Ask in side chat` 已确定跳过，「引用到新对话」替代入口也已排除。用户通常通过直接向 Codex 表达需求来发起相关新对话。

### 参数生效规则

`0.5.0-preview` 的已有行为如下。

- 新建对话可以使用 Codex 默认参数，也可以选择模型与思考深度
- 已有对话在手机保存下一轮发送参数，发送时应用
- 执行中追加使用当前轮次参数

本次要求改善基本属性的入口与查询速度。保存选择时是否立即修改桌面会话默认参数，尚待核对具体期望；当前规格保留上述已交付生效规则。

### 身份验证与编辑边界

普通 HTTPS 授权链接已有手机打开入口。依赖桌面专用服务的身份验证，以及手机无法完整展示的特殊表单，显示具体说明并交由电脑处理。

当前桌面原生编辑接口将正文中的 `## My request:` 和 `## My request for Codex:` 作为上下文分隔标记。命中该限制的消息显示编辑限制原因并保留草稿，阅读与选段功能继续可用。包含选段上下文的消息也需按该限制处理，该限制随桌面接口适配情况复核。

## 界面与状态

整体采用简洁的浅色界面，以 Qoder 移动端截图为主要参考，保证正文、点击区域和常用操作适合手机。模型参数、任务设置与消息操作的参考方案见决策记录。

- 聊天标题、项目或目录信息、运行状态和设置入口集中在一个顶部栏
- 设置使用齿轮图标，刷新使用旋转图标表达正在加载
- 设置页和弹窗的返回入口统一放在左上角，Android 系统返回键返回当前层级
- 返回设置前的页面时保留当前对话、草稿和阅读位置
- 首次读取、同步最新消息、加载更早消息分别反馈进度，已有内容在同步期间继续可读
- 单个对话历史读取失败时显示该对话的错误与重试入口，连接状态按实际连接结果显示
- 页面和所有弹窗避让系统状态栏与底部手势区域，内容超长时可滚动并能到达确认操作

| 状态或提示 | 含义与显示要求 |
| --- | --- |
| 已连接、重连中 | 手机与电脑服务及桌面连接的实际可用状态 |
| 正在读取对话 | 首次读取历史 |
| 正在同步最新消息 | 已有内容的最新状态同步 |
| 读取更早消息的加载反馈 | 分页请求仍在进行，忙碌状态持续至请求结束 |
| 进行中 | 当前对话正在执行任务 |
| `idle` | 内部空闲状态，列表和聊天页均隐藏该标签 |
| 等待处理请求 | 存在需要用户审批或回答的请求 |
| `notLoaded` | 内部执行实例的加载状态，用户界面隐藏该值；历史可读性由历史查询结果判断 |

「未加载」此前因作用不明已去掉。本次曾提出重新显示，用户已再次纠正，该显示已撤回。用户随后确认去掉「空闲」。列表和聊天页隐藏 `idle` 与 `notLoaded`，任务执行、待处理请求和异常继续明确反馈；历史读取失败另行提示。

### 过程折叠与回答选段

- 同一轮中连续的中间进度、思考摘要和工具记录合并到一个「执行过程」，默认折叠；用户消息、最终回答、待回答问题和附件保持可见
- 展开「执行过程」后，连续工具记录合并为一个「工具记录」，连续思考摘要合并为一个「思考摘要」，多个记录时显示数量；不同类型或中间进度分隔的记录各自保留顺序，展开后直接查看各条内容
- 执行中显示「执行中…」和最近一条进度摘要；手动展开或折叠后，实时更新及历史前插继续保留当前展开状态
- 旧消息缺少明确阶段时保持正文可见，避免误折叠最终回答
- 选中回答正文后自动显示悬浮的「添加到对话」，点击后保留该片段并填写意见；消息末尾不再显示该入口
- 悬浮入口跟随可见选区，并避让系统安全区；清空选区、切换页面、打开弹窗或点击输入框时收起。横屏阅读区过窄时可临时显示在阅读区之外，保持入口可操作
- 选段原文只读，可填写意见；已添加的卡片支持修改意见、重新选取其中的文字和移除，同一草稿可包含多个选段
- 选段卡片与输入草稿分别保存，重新打开或刷新后恢复；只有确认发送成功才移除已发送卡片，发送期间新写的正文继续保留
- 发送使用桌面可识别的 `response-annotations` 上下文，保留来源消息标识及所显示文本的 UTF-16 选段位置；历史、实时显示与 SQLite 缓存保留选段信息

## 历史缓存与同步

用户要求已看过的对话能够快速恢复，避免每次打开都重新等待全部历史。采用原生 SQLite，支持缓存读取、分页和事务保存。最近一轮可能因误发送后编辑而改变，包括已经结束的轮次，编辑后的整轮结果需要重新同步。

同步与数据处理需要覆盖以下行为。

- 先显示已有缓存，再获取最新内容
- 历史分页读取，长对话能够继续向前加载
- 手机切后台、网络恢复和应用重启后重新同步当前对话，保留草稿
- 编辑或回退后，根据轮次和消息身份替换受影响内容，迟到响应按请求归属处理
- 消息与同步位置在同一事务中保存，发送请求用稳定标识查询原操作回执
- 减少重复传输和大对象处理，基本属性查询避免受正文读取拖累

当前实现保留每个已缓存对话最近 10 轮，历史接口每页读取 100 个条目，实时响应限制在最近 10 轮内的最后 100 条可显示消息。这些数值属于现有实现参数。真实长对话的首屏、翻页、编辑后恢复和持续更新性能仍需验收。

桌面实时流已核实存在 `baseRevision/revision`，用于判断增量连续性。持久消息的逐条编辑版本号尚无已确认依据，历史同步应依据已核实接口。手机与服务之间当前采用有限范围的实时快照，原方案中“只传新增文本”的性能目标仍需按实际实现复核。

### 属性同步与耗时核查

- 当前会话的运行状态、模型和思考深度随桌面 IPC 快照与版本化增量更新；服务长轮询在变化到来时返回，15 秒为无变化时的最长等待，手机收到后约 120 ms 发起下一次请求
- 断线时清除已确认的运行状态，重连重新取得快照。上述行为保证按接收到的版本更新，手机网络下的端到端延迟仍待实测
- 可选模型目录每次打开选择器重新查询，读取期间显示进度。已有选项用于先行操作，刷新结果保留用户正在编辑的选择
- 手机置顶操作成功后同步当前页面与列表。桌面上另行修改置顶，目前通过手机列表刷新同步，当前接口未接入置顶变化事件
- 本机复测置顶 API 约 2576 ms，直接调用桌面 `list_threads(recent)` 约 2597–2699 ms，`list_threads(history)` 约 56 ms。旧置顶查询等待整份最近对话及侧栏数据，再提取单个置顶值；耗时集中在桌面聚合接口内部，更细的内部等待构成尚未确认
- 同次本机复测模型目录约 175 ms、会话参数约 19 ms。前述五分钟缓存仅减少目录查询次数，无法解释手机上单次请求的额外等待
