## 本地开发

```sh
npm ci
npm run dev
```

浏览器可预览页面。原生 SQLite 检查在 Android APK 内运行。

```powershell
npm test
npm run build
cargo test --manifest-path server/Cargo.toml --locked
cargo run --manifest-path server/Cargo.toml -- --web-dir=dist
```

```sh
npm run android:sync
```

该命令构建 H5 并同步 Android 工程。安装包由 Actions 中的 `Android verification` 工作流生成。Android SDK、JDK 和 Gradle 构建环境由 CI 提供。

`npm ci` 会应用当前 Capacitor 8.6.0 的回复通道顺序补丁，修正页面跳转后快速原生响应可能丢失的问题。依赖升级时需复核 `scripts/patch-capacitor-android.mjs`，依据见[决策记录](决策记录.md#2026-11-14-首页筛选与菜单分组)。

## Reach 通信版本

H5 从根目录 `package.json` 读取发布版本，Android 构建使用同一值作为 `versionName`。Windows 服务使用 `server/Cargo.toml` 的包版本。发布时两者须完全相同，包括 `-preview` 后缀。

业务接口统一位于 `/api/<发布版本>/`，状态查询和原生通知轮询也使用该路径。客户端首次业务请求先核对状态响应中的 `version`。已鉴权的异版或无版本请求返回 HTTP 412。同版路径下不存在的接口返回 HTTP 404。电脑本机设置页和取得阅读授权后的文件资源继续使用各自的地址。

Windows CI 构建完成后运行 `python -X utf8 scripts/check-api-version.py server/target/release/codex-reach-server.exe`，用临时数据库验证拒绝错版请求后没有新增上传记录。

## Windows 桌面接口

服务连接当前用户的 `codex-app-tools-*` 和 `codex-ipc` 命名管道。工具管道提供项目、会话、新建以及向未加载会话投递消息的入口。历史读取使用 `codex app-server --stdio` 的 `thread/read` 和 `thread/items/list`，每页 100 个条目，并通过同一读取会话查询模型目录。消息继续由桌面客户端执行。IPC 提供实时快照、版本化增量、参数更新、发送、停止、审批和原生编辑入口，手机实时响应保留最近 10 轮内的最后 100 条可显示消息。上述接口曾核对的版本为 Codex Windows `26.1106.6628.0`，电脑须能执行 `codex` 命令。

## Android 构建与覆盖安装

固定签名由仓库 Secrets 中的 `ANDROID_SIGNING_KEYSTORE`（PKCS12 文件的 Base64 内容）和 `ANDROID_SIGNING_PASSWORD` 提供，别名为 `codex-reach`。本机另有签名文件和口令备份。构建产物的 `signing.txt` 保存公开证书指纹。手动触发工作流时，可填写先前固定签名构建的 `upgrade_run_id`，验证证书一致、覆盖安装成功，以及 SQLite 验证库中的记录在更新后保留。

1. 打开 Actions 中成功完成的 `Android verification` 运行
2. 下载 `codex-reach-verification-运行编号` 产物，解压取得 `app-debug.apk`
3. 安装 APK，从连接页打开「SQLite 检查」，点击「运行全部检查」，确认全部通过并记录数据标记
4. 在系统设置中强行停止应用，重新打开后点击「检查已保存数据」，确认检查通过且数据标记一致

当前 CI 使用 Android 16 x86_64、4 KB 页大小的模拟器。16 KB 页大小环境的运行验证待完成，静态对齐检查结果可在产物中查看。

## 回归范围

连接页的「SQLite 检查」使用独立验证库。

- 从 WebView 通过 Capacitor 调用 Android SQLite 插件
- 批量写入 1000 条合成消息，按会话分页读取
- 在同一事务中替换最新轮次并保存同步位置
- 写入中途触发主键冲突，检查消息与同步位置均已回滚
- 关闭并重新打开连接后读取数据
- 在 CI 中停止应用进程，重新启动后核对消息、同步位置和持久化标记

CI 还检查 APK 签名、ZIP 16 KB 对齐和 64 位原生库 ELF 加载段对齐。

工作流还检查错误密钥、项目与会话加载、HTTP 消息发送、实时回复、Markdown 清理，以及强行停止进程后在离线状态读取聊天缓存和草稿。交互回归覆盖刷新图标旋转、设置页左上角与系统返回、重新连接原会话、列表与聊天的断线恢复、单个会话读取失败时仍显示已连接，以及空标题响应的缓存保存。Windows 服务执行 Rust 单元测试，并构建可执行文件。

指定 `upgrade_run_id` 后，旧 APK 先写入合成数据，新 APK 安装后再打开同一验证库。业务聊天缓存的旧表迁移由 `scripts/cache.test.mjs` 单独检查。各版实际执行的桌面、模拟器和真机检查见[版本记录](../CHANGELOG.md)。

页面显示每项检查耗时。合成数据与 CI 模拟器耗时用于初步验证，真实长对话和手机性能另行测量。

## 数据与配置

验证数据库使用合成数据。实际聊天缓存保存在手机应用目录，服务配置和发送记录保存在电脑的运行目录。仓库忽略数据库文件、`.env`、日志、keystore 和构建产物。Android 关闭 Capacitor 调试日志，服务日志只记录启动地址和运行错误。
